## 3. A 批：同步自愈、上传弹窗、报表页外观、配置注释

### 3.1 需求 5：同步状态读取失败不再永久禁用按钮

根因（三条叠加，均已复核成立）：

1. `frontend/src/pages/DatasourcePage.tsx` 轮询请求失败时把**所有行的 `schema_sync` 覆盖成 `{status:'unknown'}`**，丢失真实状态。
2. 「同步表结构」按钮的禁用条件包含 `unknown`，于是立刻变灰。
3. 轮询 effect 只在存在 `running/cancelling` 时启动；状态被改成 `unknown` 后**轮询停止**，页面不再自愈，只能手动刷新。

后端 `src/api/routes/datasource.py` 的状态查询有单源 5 秒、整批 8 秒预算，超时降级 `unknown`，是 `unknown` 的来源，但不是「永久变灰」的成因。

契约：

- `unknown` 与「读取失败提示」都**不是终态**，必须继续轮询；只有全部行落到 `idle/succeeded/cancelled/failed` 时才停表。
- 读取失败**只写行级提示**，不得覆盖 `schema_sync.status`。
- `unknown` 表示「没读到状态」，**不等于「正在同步」**，不得据此禁用「同步表结构」。
- `phase === 'publishing'` 时「终止同步」保持禁用（后端返回 409），但必须给出原因说明。
- 后端状态查询的失败模式与客户端 30 秒超时保持不变，不放宽预算。

### 3.2 需求 6：上传弹窗状态重置与滑块宽度

- 上传弹窗每次打开都必须是干净表单：文件列表、标签、数据源、分类、知识范围、切块参数全部重置。采用「打开时重置」，避免关闭动画期间闪变。
- 块大小与重叠两个滑块当前渲染成零宽（只剩一个圆点）。宽度问题在 `KnowledgePage.tsx` 内用显式宽度约束解决，不依赖全局样式。

> 注：本条**不涉及**数据库去重或同名覆盖。用户已明确残留数据是弹窗表单状态。

### 3.3 需求 7：报表页面统一外壳

根因：主题变量由 `TemplateScope` 只注入 `.report-document` 容器，而公开分享页不套全局 Layout、`body` 无背景，于是主题方块坐在白底之上；私有查看页的顶栏虽然也带 `.report-document` 类，却在 `TemplateScope` 之外，走 CSS 回退值，与正文主题不一致。

契约：

- 私有查看页与公开分享页共用一个页面级外壳：背景铺满视口并取模板底色，内容限宽居中。
- 工具栏进入 `TemplateScope` 作用域，与正文消费同一套主题变量。
- 分享页保留顶栏（公开快照标识、版本、模板切换）。
- 加载态、错误态、锁定态与正常态使用同一外壳，不出现两套观感。
- 纯样式/布局改造，不改动页面 DSL 与数据契约。

### 3.4 需求 9：配置文件参数注释

范围仅限 `.env.example` 与 `config/app.example.yaml`（`.env` 与 `config/app.yaml` 已被 gitignore，属运行配置，不修改）。

- 每个参数补齐「用途 + 默认值 + 生效范围」三要素中文注释；被整块注释掉的可选块逐条注释。
- 补全代码读取但示例缺失的参数，至少包括 `APP_CONFIG_PATH`、`TESTDATA_*`、`DJANGO_SETTINGS_MODULE`。
- 删除全仓库无引用的参数；仅供 compose/Dockerfile 使用的参数保留并注明使用方。
- 新增守卫测试，断言示例文件中的键都有注释，防止后续新增参数漏注释。

## 4. C 批：链接管理与访问统计

### 4.1 数据模型

新增两张表（迁移 `030`）：

- `report_share_visits`：一次分享访问的明细。字段含 `share_id`、`report_id`、`tenant_id`、`visitor_kind`（`user` / `anonymous`）、`user_id`（匿名时为 NULL）、`ip_hash`、`started_at`、`last_seen_at`、`duration_seconds`、`unlocked`。索引覆盖 `(tenant_id, share_id, started_at DESC)` 与 `(tenant_id, user_id, started_at DESC)`，启用 RLS。
- `report_tenant_settings`：租户级报表设置。首批字段为 `record_share_visitor_identity`（需求 3.2 开关）与 `max_permanent_reports_per_user`（需求 2.4 限制）。

### 4.2 访问时长采集协议

服务端无法得知停留时长，采用前端埋点：

1. 打开分享页上报一次访问，取得 `visit_id`。
2. 只累计 `document.visibilityState === 'visible'` 的时间；可见性变化时结算，隐藏期间不计。
3. 定时心跳上报**累积值**（幂等覆盖，非增量累加），避免重试导致重复计数。
4. 页面卸载用 `navigator.sendBeacon` 发送最后一次累积值。

### 4.3 接口与权限

- `GET /report-workbench/shares`：租户内分享平铺列表，支持按报表、创建人、状态（有效/已撤销/已过期）筛选与分页。租户管理员看全租户，其他角色只看自己创建的。
- `GET /report-workbench/shares/{share_id}/visits`：最近访问的系统用户及其停留时长。
- `POST /report-workbench/shares/batch-revoke`：批量撤销。
- `PUT /report-workbench/admin/tenant-settings`：租户管理员维护租户级设置；`GET` 读取。

### 4.4 身份记录开关

分享读取路由在访问策略中是 `auth=optional`，登录用户打开分享链接时中间件会带上真实身份。开关关闭时，即使请求携带身份也按 `anonymous` 记录，不写 `user_id`。

## 5. D 批：额度重置

- `POST /report-workbench/admin/quota-usage/reset`：单用户、批量与全租户共用同一入口，请求体 `{"user_ids":[...], "all_users":false, "fields":[...]}`；`user_ids` 与 `all_users: true` 互斥且必居其一（同时出现、都不提供或空 `user_ids` 均 422），`fields` 为**要清零的字段多选**，取值限于 `jobs_created`、`runs_started`、`llm_tokens`、`share_links` 四个按月累计字段，空数组或未知字段名返回 422。
- 只把当前周期的 `report_quota_usage` 对应列清零，**不改动 `report_quota_policies` 的上限**。
- 响应 `{"reset_users":N,"fields":[...],"period_start":"...","period_end":"..."}`；`reset_users` 是**实际被清零的用户数**，跨租户目标与本期无用量行的目标不计入，且不让整次请求失败。
- 每个被实际清零的用户各写一条 `report_access_audit`（`action="quota_usage_reset"`，`metadata` 含目标用户与字段）。
- 仅租户管理员可调用，其余身份 403。
- 字段白名单必须来自唯一来源（`src/reporting/quota_reset.py`），**禁止把请求里的字段名拼进 SQL**；持久化分支用 `RETURNING user_id` 确认实际被清零的用户。

## 6. E 批：数据源同步排队

- 去掉 `len(self.tasks) >= 3` 的硬编码 429 拒绝（该限制值此前既不在配置里也不可调），改为排队。
- `schema_sync_jobs` 的状态枚举新增 `queued`；同一数据源仍只允许一个活动任务，重复启动保持 409。
- 排队任务由调度循环按先进先出认领，认领后进入 `running`。
- 崩溃回收逻辑必须区分「无主运行任务」与「排队中任务」，不得把排队行误判为失败。
- 界面显示「排队中（前面还有 N 个）」，`N` 由服务端按同租户同数据源队列位置计算。

## 7. B 批：报表工作台重构与通知模块

### 7.1 三个子菜单与能力键

父菜单「报表工作台」保留 `report.menu` 作为可见性开关；三个子页各配能力键：

| 子页 | 路径 | 能力键 | 默认角色 |
|---|---|---|---|
| 创建报表 | `/report-workbench/create` | `report.create_page` | `tenant_admin`、`analyst` |
| 报表信息 | `/report-workbench/jobs` | `report.list` | `tenant_admin`、`analyst`、`viewer` |
| 链接管理 | `/report-workbench/links` | `report.link_manage` | `tenant_admin`、`analyst` |

旧路径 `/report-workbench` 重定向到创建报表页。菜单隐藏只是体验优化，所有 API 仍在服务端按能力键鉴权。

### 7.2 计划后台生成

计划生成从同步请求改为后台任务，状态机复用现有枚举并新增一个失败态：

```text
点「生成计划」→ planning（生成中）
  ├─ 成功 → draft（未生成）+ 个人通知
  └─ 失败 → plan_failed（计划失败）+ 个人通知
用户在报表信息中查看/编辑计划（删减发散单元、改执行方式与调度）
点「生成」→ 预占 jobs_created → immediate 入队 / scheduled 交由调度器 → queued
```

- 点「生成计划」只创建记录并启动后台规划，**不预占** `jobs_created`（需求 1.5）。
- 计划结果写入该记录的 `plan_json`；`report_jobs` 新增 `title`、`divergence`、`datasources_json` 列，使报表信息列表无需解析 JSON 即可出列。
- 计划失败可重试，重试创建新的规划尝试并重新通知。
- `POST /plans` 与 `POST /jobs` 的旧「先预览后确认」链路由新的报表资源接口取代。

### 7.3 报表信息列表

列：报表摘要标题、选择的数据源、发散档位、任务状态、运行次数、下次运行时间、创建时间；默认按创建时间倒序。租户管理员可按用户筛选；其他角色只返回自己的记录。

### 7.4 多页面

每次成功运行产生的页面**独立可访问**，不再只保留一个最新版本指针。页面列表在「报表信息」内按报表展开，支持逐页延期与设置永久。延期与永久能力下放给非管理员角色，但受租户级 `max_permanent_reports_per_user` 限制。

### 7.5 通知模块

- 通知主体统一为一条通用通知记录，覆盖四类：平台通知（超管发布）、租户通知（租户管理员发布）、指定用户群通知、任务执行完毕的个人通知。
- 渠道配置**租户级**，原服务器级 `automation_smtp_*` 配置废弃。站内信为默认已启用渠道；邮件/飞书/Slack 的发送实现先保留配置面与分发接缝，默认不启用（需求 1.9「先不发」）。
- 支持已读/未读标记、未读角标与删除。
- 引入 WebSocket 推送新通知；连接鉴权复用现有 HttpOnly Cookie/JWT 身份，推送只包含通知标识与摘要，不含报表正文或敏感数据。
- 旧的 `analysis_notifications` 表与 `/automation/notifications` 接口删除；「自动化」菜单与页面一并删除。

## 8. 测试与验收要求

- 每个需求点至少一个单元测试，覆盖正常路径、边界与回退路径；方法与组件补中文注释。
- 前端契约测试沿用 `tests/test_frontend/` 的 Python 静态断言风格。
- 涉及数据库方言的部分（额度重置、分享访问查询）覆盖 PostgreSQL 与内存/SQLite 两条分支。

- 不引入 SPEC 未声明的重量级依赖。
