# 47. 可替换嵌入模型与自动重编码

## 1. 背景

当前嵌入模型是 `all-MiniLM-L6-v2`（英文句子相似度模型，384 维），由配置项
`embedding_model_path` 指定目录。它在中文检索场景下表现很差：实测
「广告归因收入与订单净销售额的对比」的语义 top-20 全是 weather / tourism /
consumer_trends 类表，真正相关的 `insight_order_attribution` 连前 50 都进不去，
模型据此判定「白名单中不存在广告归因事实表」而拒绝生成 SQL。

根因是模型语种不匹配，不是检索链路缺陷。候选替换模型：

| 模型 | 维度 | 大小 | 语种 | 需要查询前缀 |
|------|------|------|------|-------------|
| `all-MiniLM-L6-v2`（现状） | 384 | 22M | 英文 | 否 |
| `paraphrase-multilingual-MiniLM-L12-v2` | 384 | 118M | 50+ | 否 |
| `paraphrase-multilingual-mpnet-base-v2` | 768 | 278M | 50+ | 否 |

**不同机器的算力配置有差异**（768 维模型的编码开销明显高于 384 维），所以模型选择
属于**部署侧配置**，不引入运行时热改或后台界面。

## 2. 目标与非目标

**目标**：通过环境变量选用哪个嵌入模型；换模型后数据不丢、可回滚、无需运维记忆
额外步骤。

**非目标**：

- 多模型并存、检索结果融合
- 多模型对比评估（本设计预留接口位，但不实现）
- 按租户或按用户配置模型
- 模型查询前缀支持（本设计预留元数据位，但不实现）

## 3. 核心约束

**嵌入模型的向量空间互不兼容。** 换模型必须全量重新编码，且新旧向量**不能混存**——
维度相同会静默返回错误结果，维度不同会直接报错。因此：

- collection 必须按模型隔离，不能共用
- 「只把维度改成可配置、collection 名不变」是不可接受的做法（等于埋一颗静默数据损坏的雷）

**向量写入是分散的。** `schema_manager`（表结构）、`upload_manager`（知识文件）、
`system_scanner`（系统扫描）、`business_rules`、`long_term_store`（长期记忆）五处各自
写入，**没有统一重放入口**。所以重编码的源不能是「重新触发各业务写入」，只能是
**旧 collection 的 `content` 字段**——它本身就是编码输入（表结构条目形如
`customers，包含字段: id(NUMBER), city(VARCHAR2), ...`，知识文档是正文片段，
长期记忆是记忆正文）。

## 4. 组件设计

### 4.1 模型特性适配（`src/memory/embedding_backend.py`）

把模型差异收敛到本模块内部，对外接口统一：

```python
load_embed_fn(model_path: str) -> tuple[EmbedFn, EmbeddingMeta]

EmbeddingMeta:
    dim: int              # 向量维度，从模型自动探测
    max_seq_length: int   # 最大序列长度
    query_prefix: str     # 查询侧前缀，本设计恒为空
    passage_prefix: str   # 文档侧前缀，本设计恒为空
```

**维度自动探测**：优先读 ONNX session 输出的最后一维；该维是动态符号时，回退读
模型目录 `config.json` 的 `hidden_size`。两者都拿不到 → 失败关闭（不带着错误维度建
collection）。

`MAX_SEQ_LENGTH` 由模块常量改为从模型元数据读取，默认 256（与现有行为一致）。

引入 `query_prefix` / `passage_prefix` 的**位置**但值恒为空：将来接入 BGE 系
（查询侧需要「为这个句子生成表示以用于检索相关文章：」前缀）或 E5 系
（`query:` / `passage:` 前缀）时只改本模块一处，重编码命令与启动流程不变。

### 4.2 模型指纹与 collection 命名（`src/memory/vector_store_milvus.py`）

```
指纹 = sha256(f"{模型目录名}:{维度}").hexdigest()[:8]
collection = f"data_agent_knowledge__{指纹}"
```

`_DIM = 384` 由模块常量改为实例属性，由 4.1 的元数据注入。

启动日志同时输出**完整模型路径 + 维度 + collection 名**，让运维一眼确认生效的是哪个
模型。

### 4.3 启动时的索引状态检测

**在服务就绪之后执行，不阻塞主流程**（重编码是异步后台任务，启动流程不等待它完成）。

```
目标 collection = data_agent_knowledge__<当前模型指纹>

├─ 不存在
│    └─ 创建空 collection
│         └─ 存在可迁移源? → 触发后台重编码；否则记告警
├─ 存在但为空
│    └─ 存在可迁移源? → 触发后台重编码；否则记告警
└─ 存在且有数据
     └─ 正常启动
```

**可迁移源的判定**（按优先级取一个，且必须超过最小条数门槛，默认 10 条，避免拿空壳当源）：

1. **同前缀的其它 collection** 中数据最多的那个。「同前缀」= collection 名以
   `data_agent_knowledge` 开头且不等于目标 collection —— 因此首次升级前的历史名
   `data_agent_knowledge`（无后缀）本身也在候选内
2. 都不满足 → 不迁移，记一条「新索引为空，请确认是否需要迁移」的告警

**不想要旧数据时**：删掉旧 collection 再重启即可，无需额外开关。

### 4.4 后台重编码

**并发保护**：重编码前抢占 PG advisory lock（与 `schema_sync` 的跨 worker 协调同源）；
抢不到说明别的 worker 正在跑，跳过并记日志，避免多 worker 同时重编码。

**执行方式**：分批读取源 collection 的 `content` → 用当前模型编码 → 写入目标
collection。`upsert` 幂等，中断后可重跑。

**窗口期**：重编码期间检索会返回不完整结果——新模型编码的 query 与旧 collection 的
向量不兼容，无法「先拿旧的顶着」。期间的日志明确标注「索引重建中」，便于运维判断
何时对外开放。

**进度可观测**：每批写入后记录已完成条数，完成后记录总数与耗时。

### 4.5 手动命令

```
python -m src.memory.embedding_reindex [--source <collection>]
```

用途：故障恢复、强制重跑、显式指定源。

只初始化向量库，**不启动 web 服务、不拉起 LLM / checkpoint 等无关资源**。

## 5. 操作流程

```
① 改 .env 的 embedding_model_path → 指向新模型目录
② 重启服务 → 立即就绪（不等待重编码）
③ 系统自动：建新 collection → 检测到可迁移源 → 后台重编码 → 完成
④ 旧 collection 原样保留，改回环境变量即可回滚
```

## 6. 错误处理

| 场景 | 行为 |
|------|------|
| 源 collection 不存在或为空（手动命令） | **报错退出**，绝不产出空索引 |
| 源 collection 不存在或未超门槛（启动检测） | 记告警，不执行重编码 |
| 编码或写入失败 | 中止并报告已完成条数；`upsert` 幂等，可重跑 |
| 维度探测失败 | 启动即失败，不带着错误维度建 collection |
| 抢占不到重编码锁 | 跳过并记日志（另一 worker 在执行） |

**为什么空索引比报错更危险**：检索会静默返回空，上游据此判定「没有相关知识」，
进而拒绝生成 SQL——现象与「模型能力不足」完全一样，排查成本极高。

## 7. 测试

| 用例 | 断言 |
|------|------|
| 指纹稳定性 | 同名同维度 → 同指纹；模型名或维度任一变化 → 不同指纹 |
| 维度探测 | 对真实 ONNX 模型读出 384 / 768 |
| collection 命名 | 命名规则与 `_DIM` 注入正确 |
| 重编码幂等 | 连跑两次结果一致（覆盖而非追加） |
| 源缺失（手动命令） | 报错而非静默成功 |
| 源缺失（启动检测） | 记告警且不启动重编码任务 |
| 并发保护 | 锁被占用时跳过 |

## 8. 预留（本设计不实现）

- **模型对比评估**：注册多个模型、拿真实 query 离线跑分（目标表是否进 top-20），
  数据出来再决定启用哪个。接口位在 4.1 的元数据与 4.2 的指纹机制上已经具备。
- **查询前缀**：`query_prefix` / `passage_prefix` 位置已留，接入 BGE / E5 系时填充即可。
